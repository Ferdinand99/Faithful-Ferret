# Operations register

Every vector case names an `op`. This register maps each `op` to the Rust
function that runs it, the WASM method that exposes it, and the shape of the
case's `input`. The Rust, Node and browser runners are table-driven from this
list. A case may only use an `op` that is listed here.

Rows are added by the task that introduces the operation. The first column
holds the op name in backticks.

## Key order and newer schemas

Bodies and manifests are written with the known keys first, in the order of the schema, and then the unknown keys in the order they were read. This holds at every level where unknown keys are kept: the top level of a body and inside each field, url, `totp` and `passkey`; the top level of a manifest and inside each method entry. An unknown key that stands before a known key when it is read is therefore written after the known keys. The order of the known keys is the order in which the schema lists them (for a manifest: `v`, `vk_epoch`, `methods`; for a method entry: `t`, `id`, `g`, `c`). Two implementations agree on the bytes of a sealed body or manifest only if they follow this rule.

A body whose `schema` is above 1 is read-only. It is shown and exported but never sealed (`read_only_schema`), and it is written back as the value that was read: the same keys in the same order, with nothing added, dropped or typed. A known key whose value does not fit the schema of this version is not an error in such a body and is not repeated; it is simply part of the value that was read. This is what `item.open` returns for it and what the plain JSON export writes. The CSV export and the encrypted export do not take such a body (`unsupported` and `read_only_schema`).
