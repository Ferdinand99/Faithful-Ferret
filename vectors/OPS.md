# Operations register

Every vector case names an `op`. This register maps each `op` to the Rust
function that runs it, the WASM method that exposes it, and the shape of the
case's `input`. The Rust, Node and browser runners are table-driven from this
list. A case may only use an `op` that is listed here.

Rows are added by the task that introduces the operation. The first column
holds the op name in backticks.

## Server operations

The `server.*` operations belong to the server library (`crates/ferret-server-auth`). They are `native-only`: the WebAssembly package has no server half, and the Node and browser runners do not read `server-opaque.json` or `server-secrets.json`. The independent reference in `tools/xcheck` reads them and works out the values that follow from the layouts below. The OPAQUE messages cannot be worked out by hand: `server.register_response`, `server.login_start`, `server.login_finish` and `server.replace_authorize` are recorded from the server library and are regression pins. What ties that code to the standard is the test against RFC 9807 (`crates/ferret-server-auth/tests/rfc9807_server.rs`). `xcheck` lists these four as not covered.

A *purpose* is `{ "type": "login" }` or `{ "type": "reauth", "session": hex32, "account": hex16 }`.

**Secret file.** `magic "FSEC" (4) ‖ version (1) ‖ kind (1) ‖ suite (1) ‖ length (u16 big-endian) ‖ payload ‖ SHA-256 of everything before it (32)`. The version is `0x01`, the suite `0x01`; the kind is `0x01` for `opaque_setup` (payload 128 bytes: OPRF seed 64, private key 32, dummy public key 32; the file is 169 bytes) and `0x02` for `prelogin_secret` (payload 32 bytes; the file is 73 bytes). Decoding checks, in this order, and the first defect decides: the bytes that are there of the magic (a file that is empty or shorter than four bytes and right so far is not a magic defect) are `FSEC` (`bad_magic`); the file holds the nine bytes of the header (`bad_length`); the version is 1 (`unsupported_version`); the kind byte is the one asked for (`wrong_kind`, also for a kind byte that is no kind); the suite is 1 (`unsupported_suite`); the length field is the payload length of the kind (`bad_length`); the file holds the payload and the 32 checksum bytes (`bad_length`); nothing follows the checksum (`trailing_bytes`); the checksum is right (`bad_checksum`).

**Fingerprint of the set-up.** `SHA-256("ferret/v1/setup-fp" ‖ payload)` over the 128 bytes of `opaque_setup`.

**Login name.** The text is put in NFKC, written in lower case (`str::to_lowercase`, no locale), put in NFKC again and trimmed at both ends of Unicode White_Space (Rust `char::is_whitespace`: it includes U+0085 and does not include U+FEFF; JavaScript `trim` differs on both). These steps repeat until the text no longer changes (at most four rounds; a name that is not stable then is refused). The result is refused (`malformed_login_name`) when it is empty, holds a control character (`Cc`) or one of the invisible format characters U+00AD, U+061C, U+180E, U+200B to U+200F, U+2028 to U+202E, U+2060 to U+2064, U+2066 to U+206F, U+FEFF and U+FFF9 to U+FFFB, or is longer than 254 bytes in UTF-8.

**Made-up credential id.** `HMAC-SHA256(prelogin_secret, "prelogin-id" ‖ name)`, the first 16 bytes, with the normalized name in UTF-8 (Fase 1 § 4.2).

**Made-up pre-login answer.** `d = HMAC-SHA256(prelogin_secret, "prelogin-hint" ‖ name)`. `a = u64 big-endian of d[0..8] mod 1000`, `b = u64 big-endian of d[8..16] mod 1000`. The profile is the first of the policy, in the order given, whose running sum of shares is above `a` (the last one if there is none). `sk_hint` is `b < sk_true_permille`. A policy is valid when its shares add up to exactly 1000, no profile is named twice, no profile is 0 and `sk_true_permille` is at most 1000; anything else is `internal`. (The vectors may name profiles that clients do not know; a server refuses those at start-up.)

**Made-up record.** `dummy_pk ‖ body`: the 32 bytes at offset 96 of the `opaque_setup` payload, then 160 bytes of `HKDF-SHA512(salt = none, ikm = prelogin_secret, info = "ferret/v1/prelogin/record" ‖ credential_id)` (RFC 5869; no salt is 64 zero bytes). 192 bytes in all.

**Key of a challenge nonce.** `SHA-256(session ‖ nonce)`, both 32 bytes.

**Sealed login state.** The key is `HKDF-SHA256(salt = none, ikm = prelogin_secret, info = "ferret/v1/state-seal")`, 32 bytes. The blob is `0x01 ‖ nonce (24) ‖ XChaCha20-Poly1305 ciphertext ‖ tag (16)`, 244 bytes. The associated data is `TLV[label "ferret/v1/server/login-state" (tag 0x01), version (tag 0x02) = 0x01, suite (tag 0x03) = 0x01, nonce (tag 0x33) = the 16 bytes of the login id]`, each field `tag ‖ u16 big-endian length ‖ value` (Fase 1 section 3.1); tag 0x33 is the field of the challenge nonce there and carries the 16-byte id here, which the length makes unambiguous. The 32 hex characters of the id are its bytes. The plaintext is 203 bytes: `expires_at (u64 big-endian) ‖ purpose (1: 0 login, 1 re-authentication) ‖ flag (1: 1 for a re-authentication, else 0) ‖ binding (48: session 32 ‖ account 16 for a re-authentication, else 48 zero bytes) ‖ credential (16) ‖ ksf_profile (1) ‖ server_login (128)`. Opening refuses with `denied`, whatever the cause: a blob that is not 244 bytes or has another version byte; a tag that does not verify (a changed byte, another login id, another key); a plaintext whose purpose byte is not 0 or 1, whose flag does not match the purpose, or that holds a binding for a login; a purpose, session or account other than the expected ones; and a `now` at or after `expires_at`.

## Key order and newer schemas

Bodies and manifests are written with the known keys first, in the order of the schema, and then the unknown keys in the order they were read. This holds at every level where unknown keys are kept: the top level of a body and inside each field, url, `totp` and `passkey`; the top level of a manifest and inside each method entry. An unknown key that stands before a known key when it is read is therefore written after the known keys. The order of the known keys is the order in which the schema lists them (for a manifest: `v`, `vk_epoch`, `methods`; for a method entry: `t`, `id`, `g`, `c`). Two implementations agree on the bytes of a sealed body or manifest only if they follow this rule.

A body whose `schema` is above 1 is read-only. It is shown and exported but never sealed as a new item (`read_only_schema`), and it is written back as the value that was read: the same keys in the same order, with nothing added, dropped or typed. A known key whose value does not fit the schema of this version is not an error in such a body and is not repeated; it is simply part of the value that was read. This is what `item.open` returns for it and what the plain JSON export writes. The encrypted export takes it too and writes it as it was read, so a backup loses nothing; an import reads it back as the same read-only body. The CSV export does not take such a body (`unsupported`).
